## Context

当前仓库已经完成教育 RAG 后端基础骨架：FastAPI 应用、健康检查、配置加载、核心枚举、基础 Schema，以及 MongoDB、Milvus、MinIO、Embedding 等外部服务适配器占位。需求文档要求一期形成课程资料、项目文档、DOCX、题库与 RAG 问答的最小可用闭环，因此内容导入需要先把原始资料转换成可检索、可追踪、可扩展的知识资产。

现有实现的关键约束是：应用启动和测试不能依赖真实外部服务；外部服务调用必须通过适配器边界；导入数据要保留课程、章节、项目、知识点、来源文件、租户和内容哈希等追踪字段；DOCX 是一期正式支持格式，但后续还需要扩展 PDF、课件、字幕、图片和视频等内容类型。

## Goals / Non-Goals

**Goals:**

- 提供从提交导入任务到解析、清洗、切片、向量化、写入元数据和向量索引的服务编排。
- 提供稳定的任务状态查询，让客户端能看到进度、阶段信息、错误原因和最终导入统计。
- 支持 Markdown、纯文本、DOCX 和结构化题库数据的首期导入，并为更多解析器保留注册入口。
- 保证知识片段和题目记录具备来源追踪、内容哈希、租户隔离字段和幂等写入依据。
- 提供离线单元测试替身，使流水线核心行为在无 MongoDB、Milvus、MinIO、模型服务环境下可验证。

**Non-Goals:**

- 不实现完整后台管理界面、权限系统、用户登录或复杂租户授权。
- 不实现生产级异步任务队列；首期可使用 FastAPI 后台任务或同步服务方法完成编排，接口和服务边界预留队列替换空间。
- 不实现 PDF、PPT、视频转写、OCR 或多模态向量检索，只保留解析器与数据字段扩展点。
- 不实现检索问答链路，只保证导入结果可供后续检索和问答服务消费。

## Decisions

### 1. 使用分层流水线编排，而不是把导入逻辑放在 API 路由中

导入入口由 `api` 接收请求并创建任务，核心逻辑放在 `services.import_service`，解析、清洗、切片和向量化分别下沉到 `processor` 与 `utils`。这样 API 层只负责协议和响应，服务层负责状态机和错误处理，处理器负责可替换算法。

Alternative considered: 在路由函数中直接完成解析和入库。该方式实现短，但会让状态更新、错误处理和测试替身耦合在 HTTP 层，后续替换后台队列也会困难。

### 2. 定义适配器协议和内存替身，保持启动与测试离线

MongoDB、Milvus、MinIO 和 Embedding 的真实客户端仍通过现有配置加载，但导入服务只依赖明确方法签名，例如保存任务、保存原始文件、批量写入片段、批量生成向量。测试使用内存实现验证编排和失败路径。

Alternative considered: 在第一版中直接连接真实服务。该方式能更快跑通集成环境，但会破坏当前 foundation 的离线启动约束，也会让单元测试不稳定。

### 3. 采用解析器注册表支持多格式扩展

解析层通过内容类型或文件扩展名选择解析器。首期解析器包括纯文本/Markdown、DOCX、题库结构化数据；每个解析器输出统一的 `ParsedDocument` 或 `ParsedQuestionSet` 中间结构，后续 PDF、PPT、字幕和多模态解析器按同一接口接入。

Alternative considered: 为每种格式写独立导入服务。该方式会让 DOCX、Markdown、题库重复实现状态更新、哈希、切片和入库逻辑，不利于维护。

### 4. 用内容哈希和来源元数据实现幂等导入

导入时计算原始文件哈希和片段内容哈希，并结合 `tenant_id`、`source_path`、`course_name`、`chapter_name` 等元数据形成稳定记录。重复提交相同内容时，服务应避免重复写入或以明确策略覆盖同源活跃片段。

Alternative considered: 每次导入都生成全新片段。该方式简单，但会造成检索重复、引用混乱和后续增量更新困难。

### 5. 首期任务执行可以同步或后台任务化，但状态机必须稳定

服务方法应支持直接执行以便测试，也可由 FastAPI `BackgroundTasks` 调用。任务状态转换统一为 `pending -> processing -> completed|failed|canceled`，进度按阶段更新，失败时记录异常类别和用户可理解的错误消息。

Alternative considered: 立即引入 Celery/RQ 等任务队列。该方式更接近生产，但会引入 broker、worker 部署和测试复杂度，超出当前一期导入闭环所需。

## Risks / Trade-offs

- [Risk] DOCX 文档中的图片、公式和复杂排版无法完整转换为文本 → 首期保留占位提示和来源位置，不阻塞正文、表格和列表内容入库。
- [Risk] 同步或 FastAPI 后台任务不适合大文件和高并发导入 → 服务边界按任务仓储和执行器拆分，后续可替换为队列 worker。
- [Risk] 外部 Embedding 或向量库失败会导致部分写入 → 编排层按阶段提交状态，失败时记录已完成阶段；实现阶段应优先选择先生成全部向量再批量写入，减少半成品。
- [Risk] 幂等策略过于严格可能跳过用户希望更新的内容 → 请求模型预留 `force_reimport` 或版本字段，后续增量更新可基于同一哈希和版本机制扩展。
- [Risk] 题库数据和文档片段的数据结构差异较大 → 中间结构区分 `KnowledgeChunk` 与 `Question`，但共享任务状态、来源追踪和哈希策略。

## Migration Plan

1. 在不改变现有健康检查和基础 Schema 测试的前提下新增导入模块、Schema 和路由。
2. 默认使用离线替身或未配置适配器时的清晰错误，避免应用启动依赖真实服务。
3. 在集成环境配置真实 MongoDB、MinIO、Milvus 和 Embedding 后，逐步启用真实适配器。
4. 如导入功能需要回滚，移除或禁用新增导入路由即可；已有 foundation 能力不受影响。

## Open Questions

- 生产环境首期是否需要异步队列，还是先用 FastAPI 后台任务满足小批量导入。
- DOCX 解析库优先选 `python-docx` 还是保留可替换接口后再评估表格、标题层级和图片占位能力。
- 结构化题库首期采用 JSON、CSV 还是 Excel 作为标准上传格式。
